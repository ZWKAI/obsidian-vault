# 财务 RPA 深度调研与开发决策报告

**研究截止日：2026-09-02｜读者：开发人员、架构师、产品与财务数字化负责人**

> 口径说明：本文将“RPA 软件”“财务自动化（Finance Automation）”“AP 自动化”“AI in Finance”视为不同市场，不相加。标注为**事实**的内容来自公开资料；**推断**是对多项事实的归纳；**判断**是面向产品决策的建议。厂商案例指标均是客户/厂商披露，并非独立审计结果。

## 1. Executive Summary

### 结论先行

1. **市场仍值得做，但不值得再造一个通用 UiPath。** Gartner 统计 2024 年全球 RPA 软件市场为 36 亿美元，同比增长 14.5%；与此同时，Gartner 认为 UI 自动化暂时没有规则型替代物，但产品重心正转向 computer use、agentic automation 与业务编排。中国公开转述的 IDC 口径显示，2024 年 RPA+AI 解决方案市场约 31.5 亿元人民币，同比增长 27.4%，产品市场约 15.3 亿元，同比增长 37.1%。这意味着需求未消失，竞争焦点却从“能点鼠标”迁移到“能把财务结果安全交付”。来源：[Gartner 2024 RPA market](https://www.gartner.com/en/documents/6842834)、[Gartner 2026 RPA market overview](https://www.gartner.com/en/documents/7488853)、[IDC 中国数据转述](https://www.eepw.com.cn/article/202507/471926.htm)。
2. **最佳切口是“垂直财务控制塔 + 可审计的混合执行”，而非纯机器人。** 首选银行对账、跨系统核对、发票校验/去重、三单匹配、凭证生成与固定报表。API 优先，RPA 只覆盖无 API 的最后一公里；OCR/LLM 负责理解，工作流负责确定性，人工负责授权和例外。
3. **AI Agent 不会在未来 2–3 年替代 RPA。** 公开基准仍显示通用 computer-use agent 在复杂桌面/企业任务上可靠性不足；OpenAI 早期 CUA 在 OSWorld 为 38.1%，2025 年 EnterpriseBench 的最佳系统任务完成率为 41.8%。它们适合建议、分类、解释和异常辅助，不宜独立完成不可逆付款或记账。[OpenAI CUA](https://openai.com/index/computer-using-agent/)、[EnterpriseBench](https://arxiv.org/abs/2510.27287)。
4. **小团队 MVP 可做，通用企业级平台不可低估。** 6–8 人、5–7 个月、约 40–55 人月可交付一个限定 ERP/银行/发票格式的可运营 MVP；覆盖通用设计器、Windows runtime、SAP/Oracle/金蝶/用友连接器、流程挖掘、HA、多租户与合规的完整平台，通常需要 20–35 人、18–24 个月以上。
5. **技术建议：** React 控制台；Go 或 Java 控制面；Temporal 作为耐久工作流；C#/.NET Windows 执行器；Playwright 浏览器自动化；Python 文档/OCR 服务；PostgreSQL；Redis；对象存储；Vault/KMS；OpenTelemetry。不要首版自研 durable workflow、OCR 基础模型、LLM、密码库、录像编解码和通用流程挖掘。

### 一句话产品定义

> 一个面向中大型企业财务共享中心的“对账与凭证控制塔”：把银行、ERP、Excel、发票和邮箱数据标准化，以确定性工作流执行匹配与过账前校验；API 不可用时调用受控 RPA；低置信度与高风险动作进入人工复核；全过程留存输入、规则版本、证据、审批与输出。

## 2. 行业背景

### 2.1 财务数字化栈不是替代关系

| 层级 | 主要职责 | 典型边界 |
|---|---|---|
| ERP/核心财务 | 权威账簿、主数据、交易与控制 | 应优先经受支持的 API/批导入集成 |
| 共享中心/费控/税务平台 | 跨组织标准流程、审批、政策 | 是流程 owner，不等于执行底座 |
| 电子凭证/电子发票 | 原始凭证数字化与结构化交换 | 中国财政部正推动 XML/OFD/PDF 嵌入 XBRL 的标准化、无纸化和自动化处理，[政策说明](https://www.mof.gov.cn/jrttts/202505/t20250521_3964264.htm) |
| OCR/Document AI | 文档分类、字段/表格抽取、证据定位 | 不能单独保证会计判断或业务真实性 |
| Workflow/BPM | 长事务、审批、SLA、补偿、人工任务 | 管理“谁、何时、依据什么” |
| RPA | 操作无 API/难改造的网页、Windows、Excel | 是执行通道，不应成为数据真相源 |
| AI Agent | 意图、文档理解、候选方案、异常解释 | 高风险动作必须被规则、权限和审批约束 |

**推断：** 财务成为 RPA 高发部门，不是因为界面操作本身有价值，而是因为跨银行、ERP、税务、邮件和 Excel 的流程存在大量“结构化但未集成”的断点；同时关账、付款、税务有周期性峰值和审计要求。

### 2.2 适合与不适合自动化的工作

适合：高频、规则稳定、输入可验证、异常比例低、系统/控件稳定、可重放且有明确成功条件的采集、比对、录入、下载和通知。

不适合直接 RPA：低频且规则持续变化、依赖商业判断、证据不完整、不可逆高金额动作、反自动化/验证码频繁、目标系统有稳定 API 却仍用 UI 绕行的流程。

### 3.2 采用率与客户结构

- **暂无可靠公开数据**可证明“全球/中国财务 RPA 企业采用率”的统一百分比。Gartner 仅给出财务 RPA 已广泛采用的方向性判断，[Finance RPA](https://www.gartner.com/en/finance/trends/finance-rpa)。
- McKinsey 2024 年对 276 名欧美职能高管的调查中，财务 GenAI 已部署/试点比例分别包括成本分析 47%、AP 审批 44%、欺诈检查 44%；这是 **GenAI 用例调查，不是 RPA 采用率**。[McKinsey](https://www.mckinsey.com/capabilities/operations/our-insights/gen-ai-in-corporate-functions-looking-beyond-efficiency-gains)
- 大型企业更容易承担 CoE、权限治理、Bot 运维和系统集成成本；中型企业更看重预封装场景、SaaS、按量计费和短实施周期。后一句是**基于成本结构的推断**，不是公开采用率统计。
- 典型客户集中在银行、保险、制造、零售、电商、物流、能源、公共事业和集团型共享中心，因为它们交易量大、系统多、审计压力高。

### 5.2 排名与边界

- **综合 Top 10：** 银企对账、余额/跨账核对、发票校验/去重、凭证生成/录入、跨系统同步/批处理、三单匹配、报表/Excel 汇总、资金日报、开票、回款核销。
- **纯 RPA Top 5：** 遗留网银流水下载、遗留系统批量录入、标准化开票、标准凭证录入、固定格式报表采集。
- **Agent Top 5（均需工作流约束）：** 催收承诺跟踪、文档分类与字段抽取、科目候选、费用合规解释、差异解释。
- **不建议 RPA：** 有稳定受支持 API 的系统集成；规则每周变化的判断；高金额付款终审；低频一次性迁移；验证码/反自动化密集操作；无稳定成功条件且证据不足的复杂异常。

关键产品证据：[UiPath Maestro](https://www.uipath.com/product/maestro)、[UiPath Automation Suite](https://www.uipath.com/product/automation-suite)、[Automation Anywhere APA](https://www.automationanywhere.com/products/agentic-process-automation-system)、[Blue Prism Enterprise](https://www.blueprism.com/products/enterprise/)、[SAP Actions](https://help.sap.com/docs/build-process-automation/sap-build-process-automation/set-up-and-use-actions-with-sap-build-process-automation)、[ServiceNow RPA Hub](https://www.servicenow.com/products/robotic-process-automation.html)、[来也产品](https://laiye.com/product)、[金智维 Ki-Agent](https://www.kingsware.cn/ki-agent)、[艺赛旗产品说明](https://support.i-search.com.cn/article/1733733045144)。

**采购判断：** 选平台时不要用“是否有 AI Agent”打勾决策。至少用 3 个真实流程做基准：成功率、P95 时延、变更恢复时间、例外率、每千笔总成本、审计证据完整率、凭证隔离、并发和灾备。

## 8. 传统 RPA 技术架构

```text
财务用户/审批人
  └─ Web 控制台：流程、工单、证据、监控、权限
       └─ Control Plane/API Gateway
            ├─ Workflow：状态机、人工任务、补偿、版本
            ├─ Scheduler/Queue：定时、事件、优先级、租约
            ├─ Policy：RBAC/ABAC、SoD、限额、四眼原则
            ├─ Secrets：Vault/KMS、短期令牌、轮换
            └─ Audit：append-only 事件、截图/录像/输入输出 hash
                 ↓ signed job + scoped credential
        Bot Runtime / Worker Pool
          ├─ API/SFTP/DB connector（优先）
          ├─ Playwright Browser Worker
          ├─ C# Windows UIA/Office Worker
          └─ Python Document/OCR Worker
                 ↓
 ERP / 银行 / 税务 / 邮箱 / Excel / OA / CRM
```

### 8.1 设计器与流程模型

- 节点规范至少含：typed input/output、schema、timeout、retry policy、idempotency key、compensation、required secret scope、evidence policy、risk level。
- DAG 适合短批处理；BPMN 适合业务可视、审批和长流程；代码型 durable workflow 适合复杂重试、补偿和工程测试。不要用一个 JSON 大对象同时承担 UI、运行语义和版本迁移。
- 流程发布必须冻结 `workflow version + rule version + connector version + prompt/model version`。运行实例永远引用不可变版本。

### 8.2 Runtime 技术路线

| 通道 | 建议 | 优点 | 主要失败模式 |
|---|---|---|---|
| Web | Playwright + 语义 locator；扩展仅用于录制/特殊注入 | 自动等待、重试、隔离上下文，[官方 locator 机制](https://playwright.dev/docs/locators) | DOM/权限/下载策略变化、验证码 |
| Windows | C# UI Automation/Accessibility；图像定位仅兜底 | 可访问控件树、类型安全、易做签名 agent | 自绘控件、远程桌面、DPI/焦点、弹窗 |
| Excel | Open XML/库处理优先；公式重算/宏才用 Office COM | 无头、快、可测试 | 公式兼容、宏、安全提示、文件锁 |
| OCR/文档 | 分类→OCR→字段模型→规则校验→人工复核 | 可输出字段置信度和证据坐标 | 版式漂移、低质扫描、语义歧义 |
| 键鼠/图像 | 最后兜底，强制截图证据和超时 | 覆盖无控件树界面 | 脆弱、难并发、误操作风险高 |

### 8.3 调度、幂等和恢复

1. 事件进入后生成业务幂等键，如 `legal_entity + bank_account + statement_date + row_hash`。
2. Worker 用租约而不是永久“占有”任务；心跳丢失后可重派。
3. Activity 重试必须区分 transient、business exception、security exception；后两类不能盲重试。
4. 外部写操作采用查询前置、唯一业务号、outbox/inbox 或补偿；“exactly once”应转化为可验证的 effectively-once。
5. 录像不是唯一证据。应保存结构化 input/output、规则命中、控件/接口响应、审批人、时间戳与对象 hash。

### 8.4 何时用 API 而不是 RPA

只要存在受支持、权限可控、性能可接受的 API/批量接口，优先 API。UI RPA 的合理条件是：无 API 或改造排期不可控；流程价值高；界面足够稳定；目标系统许可允许；动作可验证/撤销；并有 owner 接受维护 SLA。数据库直写核心财务表通常不应作为“API 替代”。

## 9. AI + RPA：受控智能自动化架构

```text
请求/事件/文档
      ↓
AI 层：分类、抽取、意图、候选计划、异常解释
      ↓  JSON Schema + confidence + evidence
Policy/Workflow：规则、权限、限额、状态、超时、审批
      ├────────────┬────────────┐
      ↓            ↓            ↓
 API Connector   RPA Runtime   Human Task
      └────────────┴────────────┘
                   ↓
       验证结果 → 审计证据 → 账务/业务结果
```

传统 RPA 的局限来自规则硬编码、UI 漂移、非结构化输入、异常长尾和维护成本。AI 可以改善“读什么、可能该怎么做、异常属于哪类”，但不能消除“是否允许做、是否成功、如何审计”。因此控制权应在 workflow/policy，而非 LLM。

| AI 能力 | 财务用途 | 必须加的护栏 |
|---|---|---|
| OCR/Document AI | 发票/回单/合同分类与字段抽取 | 字段级置信度、坐标证据、金额/税额/日期规则、抽样复核 |
| NLP/RAG | 政策问答、工单归类、催收/差异摘要 | 引用原文、文档权限继承、版本有效期 |
| LLM tool/function calling | 选择只读查询或创建候选工单 | 工具白名单、参数 schema、金额限额、无直接密钥 |
| Multimodal/Computer Use | 无结构页面理解、变更后的 UI 辅助 | sandbox、域名/窗口白名单、动作预览、关键动作人工确认 |
| Agent planning | 多步骤异常调查、生成处置建议 | 最大步数/预算、状态外置、可终止、结果验证 |
| MCP/工具协议 | 统一暴露 ERP、规则、知识库工具 | 服务身份、逐工具授权、审计、数据分级；协议不是安全边界 |

### 推荐的“确定性外壳”

- 模型只输出严格结构化对象，不直接产生 SQL、脚本或键鼠事件；结构化输出可降低格式错误，但不证明语义正确。[Anthropic structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- 模型看到 token 的引用，不看到长期密码；执行器按任务换取短期凭证。
- 每次决策保存 model/provider/version、prompt hash、retrieval document ids、tool calls、confidence 和 reviewer。
- 建立黄金集与回归集：字段准确率、误放行率、异常召回率、证据一致率、每单成本；模型升级先 shadow，再 canary。
- 高风险写操作由确定性规则重新计算参数，不能直接复用模型自由文本。

## 10. AI Agent vs RPA

| 能力 | 传统 RPA | AI Agent | AI + RPA/Workflow |
|---|---|---|---|
| 固定规则 | 强 | 中 | 强 |
| UI 操作 | 强但脆 | 可适应但成功率不稳定 | 固定路径 RPA，长尾由 agent 辅助 |
| API 调用 | 强 | 强 | 强，并可治理 |
| 非结构化文本/PDF/发票 | 弱–中 | 强 | 强，且可校验 |
| Excel | 强 | 中 | 强 |
| 异常处理 | 规则内强、长尾弱 | 建议/归因强 | 分类、建议、人工闭环 |
| 自主决策 | 弱 | 强 | 受策略约束 |
| 流程稳定性 | 稳定输入下高 | 目前中低 | 高于单一 agent |
| 可解释/审计 | 强（步骤级） | 弱–中 | 强，前提是记录证据与版本 |
| 财务风险 | 可控但可能高速复制错误 | 幻觉/越权/提示注入 | 最低：限权、校验、审批、可回滚 |
| 开发成本 | 场景构建偏高 | 原型低、生产治理高 | 平台初始高，复用后下降 |
| 维护成本 | UI 变化敏感 | 模型漂移/不可复现 | 两类维护均有，但故障可分层 |

**最终答案：未来 2–3 年是 AI + Workflow + API + RPA + Human。** RPA 负责确定性 UI 执行；Agent 负责不确定性理解与建议；Workflow/Policy 负责过程和风险。2025 年实证研究也发现 RPA 在稳定重复任务上更快、更可靠，LLM agent 开发更快、适应性更好但尚未达到生产可靠性。[Are LLM Agents the New RPA?](https://arxiv.org/abs/2509.04198)

## 11. 财务 RPA 的安全与合规

### 11.1 控制矩阵

| 风险 | 强制控制 | 不充分做法 |
|---|---|---|
| 银行/ERP 凭证泄露 | Vault/KMS、短期令牌、按 bot/实体/环境隔离、轮换、禁止日志明文 | `.env`、共享账号、流程变量保存密码 |
| 越权/职责冲突 | RBAC + ABAC、SoD、发起/审批/执行分离、JIT 授权、金额和账户白名单 | “管理员可做一切”或 bot 兼任审批人 |
| 重复/错误过账 | 幂等键、借贷/期间/主数据校验、dry-run、双重审批、补偿/反冲 | 仅看“页面出现成功” |
| 数据出域/隐私 | 数据分类、最小字段、脱敏、地域/保留策略、供应商 DPA、出境评估 | 把整张凭证/客户表直接送公共模型 |
| 提示注入/Agent 越权 | 内容与指令分离、工具白名单、参数校验、网络隔离、人工确认 | 让模型读取邮件后直接付款 |
| 证据不可追溯 | append-only 审计、结构化事件、hash/WORM、时钟同步、版本固化 | 只存截图，或日志可由 bot 删除 |
| UI 漂移 | selector 多策略、目标/金额回读、视觉差异、canary、断路器 | 无限重试键鼠脚本 |

OWASP 建议集中管理秘密、最小权限和轮换，[Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)。中国《个人信息保护法》第 24 条要求自动化决策透明、公平，并在特定情形提供说明/拒绝方式，[官方文本](https://www.miit.gov.cn/zwgk/zcwj/flfg/art/2022/art_04a0f1fb5df244e39688fd5372623a8d.html)；财务数据还要结合《数据安全法》、会计档案、企业内控和行业监管判断。[数据安全法](https://www.miit.gov.cn/zwgk/zcwj/flfg/art/2022/art_284b390b84484f10b0e43eeafaad0f6d.html)、[财政部企业内部控制基本规范](https://kjs.mof.gov.cn/zhengcefabu/200807/t20080704_55982.htm)。上线前应由法务、内控和信息安全完成适用性评估，本文不是法律意见。

### 11.2 为什么不能完全无人值守

不是所有运行都要人盯着，但**授权、例外和高风险不可被删除**：输入可能造假，规则可能过期，UI 可能漂移，主数据会变化，模型会幻觉，银行付款不可逆，且内控要求职责分离。正确形态是风险分层：低风险、可逆、规则明确且置信度高的批次自动直通；中风险抽样/阈值复核；高金额、主数据变更、税务申报和付款释放强制四眼审批。

## 12. ROI 与商业价值

### 12.1 公式

```text
年度可实现收益 =
  节省工时 × 全负荷时薪 × 现金化/可实现系数
  + 可验证的加班/外包/避免招聘
  + 错误、罚款、重复付款等期望损失下降
  + 可量化的周转资金/关账提速价值

年度总成本 =
  License + Bot/Hosted Runtime + Server/Cloud
  + OCR/LLM/文档/交易量费用
  + 开发实施摊销 + 运维 + 培训 + 安全合规 + 变更维护

ROI = (年度可实现收益 - 年度总成本) / 年度总成本
回收期（月） = 一次性投入 / 月度净收益
```

不要把“节省工时”直接当现金：只有减少加班/外包/招聘、自然减员不补或把产能转化为可验证产出时，才真正现金化。还应做直通率、例外处理时长、交易量、UI 变更频率、许可费和现金化系数的敏感性分析。

### 12.2 示例：年处理 12 万张 AP 发票（假设，不是市场统计）

| 项目 | 假设/计算 | 金额（万元/年） |
|---|---|---:|
| 原人工 | 4 分钟/张 = 8,000 小时 | — |
| 自动化后 | 75% 直通；25% × 3 分钟例外 + 500 小时运营 = 2,000 小时 | — |
| 节省工时 | 6,000 小时 × 120 元全负荷时薪 × 70% 可实现 | 50.4 |
| 错误/加班/外包下降 | 须用企业历史数据验证 | 16.0 |
| 年度收益 | 合计 | 66.4 |
| 首年成本 | 许可/云/OCR 18 + 开发实施 36 + 运维培训 14 | 68.0 |
| 稳态年成本 | 许可/云/OCR 18 + 运维变更 12 | 30.0 |

首年 ROI = -2.4%，稳态 ROI = 121.3%。若现金化系数从 70% 提升到 90%，年度收益约 80.8 万元，首年 ROI 约 18.8%。**判断：** 直通率和工时现金化往往比模型 token 单价更影响 ROI；MVP 要先证明这两项。

| 类别 | 真实痛点 | 可解决时间 | 判断 |
|---|---|---|---|
| 业务 | 规则散落在人脑/Excel；例外原因无编码；owner 不清 | 短–中期 | 先做流程/例外字典，技术不能替代治理 |

## 15. 未来 2–3 年趋势：真实变化与营销

| 主题 | 判断 | 理由 |
|---|---|---|
| API + RPA 混合自动化 | 真趋势 | 企业系统 API 增加，但遗留 UI 长期存在 |
| Workflow + Agent | 真趋势 | agent 的不确定性必须由状态、权限、审批和补偿包围 |
| Document AI + 人工复核 | 真趋势 | 财务输入仍以文档为主，字段证据可量化 |
| Computer Use | 真趋势但仅适合受限任务 | 能覆盖自绘/无 API 界面，当前可靠性与安全仍不足 |
| 自然语言生成流程 | 辅助是真，零测试上线是营销 | 可生成初稿、映射和测试，仍需 schema、评审和回归 |
| 自适应 UI 自动化 | 局部可行 | locator 修复/候选识别有效；无验证的自修复会静默误点 |
| AI 自动异常处理 | 分类/建议是真，自主处置需分级 | 低风险可直通，高风险必须人工/规则确认 |
| “一个财务 Agent 替代整个财务部” | 营销 | 权限、真实性、责任、内控、长尾和可靠性不支持 |
| Autonomous Finance | 可作为长期运营目标 | 实际会是分层自治，不是无审批自治 |

Gartner 2026 的 RPA 市场概览也把 computer use、agentic automation 和 business orchestration 列为核心趋势，同时明确传统 UI 自动化仍有作用。[来源](https://www.gartner.com/en/documents/7488853)

## 16. 自研可行性与 Build/Buy 边界

**判断：** 自研“通用 RPA 平台”性价比低；自研“垂直财务产品的控制面、领域模型、规则、证据与连接器”可行且可能形成壁垒。

| 能力 | 建议 | 理由 |
|---|---|---|
| 财务对象模型、匹配/核对规则、例外分类、证据包 | 自研 | 直接形成差异化和数据飞轮 |
| 场景模板与 SAP/金蝶/用友/银行连接器 | 自研核心适配层 | 本地实施经验与稳定性是壁垒 |
| 控制台、任务/工单、策略、SLA、价值仪表盘 | 自研 | 决定用户体验和可运营性 |
| Durable workflow | 基于 Temporal/Camunda/Flowable | 重试、恢复、版本是多年工程 |
| 浏览器 runtime | Playwright 封装 | 不重复造协议/浏览器兼容层 |
| Windows runtime | 自研薄 agent，基于 .NET UIA | 需要签名、升级、控件适配；底层 API 复用 |
| OCR/LLM 基础模型 | 第三方/开源多供应商 | 训练成本高，易商品化；应自研评估与路由 |
| Secrets/KMS/IAM | 企业 Vault/KMS/IdP | 安全基础设施不宜自造 |
| 通用 Process/Task Mining | 首版购买/不做 | 数据采集、隐私和算法复杂，非切入点 |

| P0 | API/SFTP/DB/邮件/文件连接器框架 | 中高 | 4–6 | secret scope、限流、schema、重放 |
| P0 | Playwright 浏览器执行器 | 中高 | 3–5 | 隔离 profile、下载、回读验证、升级 |
| P0 | Excel/PDF/文件处理 | 中 | 2–3 | 大文件、公式、格式/宏边界 |
| P0 | 控制台：任务、批次、工单、证据 | 中高 | 5–7 | 状态一致、检索、人工闭环 |
| P0 | IAM/RBAC/SoD/Secrets/Audit | 高 | 5–7 | 企业 IdP/Vault；越权与篡改测试 |
| P0 | 可观测、告警、部署/升级 | 高 | 4–6 | 业务 SLI、trace、灰度、回滚 |
| P1 | OCR/Document AI 路由与复核台 | 高 | 4–6 | 字段证据、置信度、标注/回流 |
| P1 | 流程版本、规则版本、测试/模拟 | 高 | 3–5 | 旧实例兼容、回归包 |
| P1 | C# Windows UIA agent | 很高 | 6–10 | 签名、自动更新、桌面会话、自绘控件 |

## 18. 技术选型建议

### 18.1 推荐组合

| 层 | 推荐 | 备选与取舍 |
|---|---|---|
| Web | React + TypeScript；React Flow/受限节点画布 | Vue 也可，团队存量优先；React 的复杂图编辑生态通常更丰富 |
| 控制面 | **Go**（小团队）或 **Java/Spring**（大型企业团队） | Go 部署轻、并发与 Temporal SDK 好；Java 在企业中间件/人才/治理更成熟；Node 不做核心调度，Python 不做统一控制面 |
| 工作流 | Temporal（代码优先 MVP） | Camunda 适合 BPMN/业务可视与企业流程平台；Flowable 适合 Apache 2.0、自托管 BPMN/CMMN/DMN；不要自研 durable engine |
| 浏览器 | Playwright | Selenium 适合既有 WebDriver 资产/多语言；Puppeteer 适合纯 Chromium 简单任务。Playwright 的 locator 有 auto-wait/retry，[官方文档](https://playwright.dev/docs/locators) |
| Windows | C#/.NET UI Automation | pywinauto 适合原型；AutoHotkey 仅 attended 小工具；WinAppDriver 适合存量测试路线，不作为新平台核心 |
| Excel | Open XML/库优先；确需公式重算/宏时隔离 Office COM worker | Python pandas 适合数据变换，但不保真复杂 workbook |
| OCR/Document | PaddleOCR 私有化基线 + 1–2 家云 OCR 基准；VLM 仅长尾 | 按字段/版式/语言实测；PaddleOCR 为开源工具链，[项目](https://github.com/PaddlePaddle/PaddleOCR) |
| 数据 | PostgreSQL + S3 兼容对象存储 + Redis | MySQL 亦可但不带来关键优势；截图/文档不塞数据库 |
| 消息 | MVP 用 Temporal task queue；Redis 仅缓存/限流 | 独立 RabbitMQ 在多协议异步集成时引入；Kafka 到高吞吐事件/审计分析阶段再用 |
| Secrets | Vault/云 KMS + 企业 IdP | 不自研，不允许流程文件携带长期密码 |
| Observability | OpenTelemetry + Prometheus/Grafana/Loki 或企业栈 | 同时监控技术指标与业务正确完成率 |

[Temporal](https://docs.temporal.io/) 提供耐久执行；其架构通过事件历史、task queue 与 worker 恢复工作流，[架构说明](https://github.com/temporalio/temporal/blob/main/docs/architecture/README.md)。需要业务人员直接维护 BPMN 时，可评估 [Flowable](https://www.flowable.com/open-source-code) 或 [Camunda/Zeebe](https://docs.camunda.io/docs/8.7/components/zeebe/zeebe-overview/)。

### 18.2 语言比较

| 语言 | 稳定/性能 | 开发与生态 | 最佳角色 | 不建议 |
|---|---|---|---|---|
| Java | 高 | 企业/ERP/治理最强 | 大型控制面、规则/集成服务 | 小团队为统一技术栈强行采用 |
| Go | 高、部署轻 | 云原生/并发优秀 | 小团队控制面、agent 管理、连接器 | Windows UI 深度自动化 |
| Python | 中 | AI/OCR/数据生态最强 | 文档、模型、数据处理 worker | 长期承担所有调度/多租户控制面 |
| Node.js/TS | 中高 | Web/自动化开发快 | BFF、浏览器 worker、前后端共享 schema | CPU 密集、关键 durable orchestration |

### 18.3 LLM 选择

不要以“谁榜单第一”硬编码供应商；构建 provider-neutral gateway，支持结构化输出、tool policy、数据地域、预算、fallback 和 eval。模型能力/价格更新频繁，上线时重查官方条款。

| 选项 | 优点 | 关键核验 |
|---|---|---|
| OpenAI | tool use/多模态/生态完整 | 端点数据保留、ZDR 资格、地区；[数据控制](https://platform.openai.com/docs/models/default-usage-policies-by-endpoint) |
| Anthropic | 长上下文、tool use、结构化输出 | API 保留/ZDR 与地区；[数据保留](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention) |
| Google Gemini/Vertex | 云数据栈、多模态、function calling | Vertex 项目地域与 ZDR；[工具调用](https://ai.google.dev/gemini-api/docs/tools)、[Vertex 数据说明](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/vertex-ai-zero-data-retention) |
| 国内云模型 | 中国区网络、采购、中文/本地合规便利 | 模型/服务地区、保留、专有网络、权限；如[阿里云区域说明](https://help.aliyun.com/zh/model-studio/regions) |
| 私有化模型 | 数据路径和版本可控 | GPU 成本、吞吐、运维、效果、许可证；“私有化”不自动等于安全 |

### 18.4 从开发到生产的关键工程细节

- Selector：role/name/test-id/DOM 多候选 + 页面/窗口/控件语义；坐标只作最后兜底。
- 结果验证：每个写动作后从独立通道回读业务号、金额、状态；截图只辅助。
- 隔离：每 bot 独立 OS 用户/profile/临时目录；任务级 secret scope；禁止复用下载目录。
- 测试：connector contract test、录制回放、沙箱端到端、故障注入、UI diff、财务黄金集。
- 发布：流程与规则不可变版本；旧实例 pin 版本；agent/runtime 采用 signed update、ring/canary/rollback。

## 19. MVP：对账与凭证控制塔

### 19.1 第一批 5 个场景

1. 银行流水导入（API/SFTP/标准文件，限定一家银行 UI 兜底）。
2. 银企/回款自动匹配：精确规则 + 可解释模糊候选。
3. 发票采集、字段抽取、验真接口适配、重复校验。
4. AP 发票与 PO/收货的三单匹配；异常进入工单。
5. 凭证草稿生成、借贷/期间/主数据校验、审批后通过一个 ERP 适配器提交。

### 19.2 MVP 必须具备

- CSV/XLSX/API/SFTP/邮件输入、统一 canonical schema、数据 lineage。
- 可配置匹配规则、阈值、优先级、规则版本和 dry-run。
- 批次/任务状态、例外队列、复核/驳回/重跑、证据包导出。
- Temporal 工作流、幂等、超时/重试/补偿；Playwright worker 和一个 ERP API/导入连接器。
- SSO、RBAC、最小 SoD、Vault、审计、监控/告警、租户/法人实体隔离。
- 指标：端到端正确完成率、直通率、例外率、P95 周期、人工分钟/单、每千单成本、MTTR、变更失败率、证据完整率。

### 19.3 明确不做

通用拖拽 Studio、任意 Windows 软件、任意 ERP、流程挖掘、自然语言直接发布、完全自治付款、全球税务引擎、自己训练 OCR/LLM、无限多租户计费。用“受限模板 + JSON/YAML 配置 + 可视运行图”替代首版通用设计器。

### 19.4 PoC 退出标准

在真实但脱敏数据上连续 4 周：关键金额/科目零误过账；端到端正确完成率 ≥99.5%（高风险动作需更高）；目标样本直通率 ≥70%；例外都有 reason code；证据完整率 100%；一次 UI/字段变更可在 1 个工作日内定位和恢复。具体阈值须由客户风险偏好确认。

## 21. 商业模式与单元经济

推荐“平台订阅 + 处理量/受管 runtime + 场景包 + 实施/高级支持”的混合模式：

| 收入项 | 计费建议 | 目的/风险 |
|---|---|---|
| 平台基础费 | 法人实体/环境/年度 | 覆盖治理、审计、控制台；避免纯人头计费抑制采用 |
| 交易/文档量 | 阶梯包量 | 与价值/成本相关；需定义重跑、失败、页数 |
| Hosted/专用 Bot | 并发 runtime/月 | 覆盖机器与运维；API-only 流程不应收 bot 费 |
| 场景/连接器包 | 银行/ERP/行业模板 | 将实施知识产品化 |
| 实施与高级支持 | 固定范围里程碑 + SLA | 防止无限定制；实施毛利应单独核算 |

销售采用 land-and-expand：一个实体、一个银行、一个 ERP、一个月结周期起步，用基线与价值仪表盘证明直通率和工时现金化，再扩 AP/AR/GL。谨慎承诺 outcome-based 定价，因为数据质量、审批时长和系统变更不完全由供应商控制。

商业可行性需跟踪：CAC 回收期、首个流程上线天数、实施/订阅收入比、毛利、每客户连接器维护小时、净收入留存、每千单云/OCR/LLM 成本、因系统变更造成的 MTTR。

## 22. 可持续壁垒

1. **财务语义与规则资产：** 发票、PO、收货、流水、凭证的统一模型；行业化匹配、容差、账期、税务和关账规则。
2. **例外语料和处置闭环：** 带 reason code、证据和最终结果的高质量例外集，比通用大模型本身更难复制。
3. **连接器可靠性：** SAP/金蝶/用友/银行的版本矩阵、contract tests、变更检测、认证和回滚。
4. **控制与证据：** SoD、策略、审批、每笔交易可重建证据包；能通过客户审计比“能运行 demo”更重要。
5. **运营基准：** 按场景/客户的直通率、例外率、MTTR、成本与价值基准，可指导阈值和售前承诺。
6. **迁移兼容：** 从 Excel/脚本/UiPath 等导入规则、测试和历史证据，降低切换成本。

不是长期壁垒：包一层 LLM API、通用聊天界面、简单拖拽画布、键鼠录制、单一 OCR 模型或“支持 MCP”标签。

## 24. 最终结论与开发者行动单

### 24.1 对 12 个核心问题的明确回答

1. **财务为何需要 RPA？** 解决遗留 UI 和跨系统最后一公里；真正需求是及时、正确、可审计的财务结果。
2. **最适合什么？** 高频、规则稳定、结构化、可验证、可回滚的采集/核对/录入；API 不可用时才优先 UI RPA。
3. **最高价值场景？** 银企/跨账核对、发票去重/三单匹配、凭证草稿与固定数据汇总。
4. **传统 RPA 与 AI+RPA 区别？** 前者按确定规则执行；后者用 AI 理解非结构化输入和长尾，但由 workflow/policy 管控。
5. **主流产品？** UiPath、Automation Anywhere、Blue Prism、Power Automate、SAP BPA、ServiceNow 与国内通用厂商；财务深度还要比较 BlackLine、HighRadius、Tipalti、ERP 财务云等邻接产品。
6. **核心架构？** 控制面、durable workflow、策略/权限、执行器、连接器、文档/AI、证据审计和可观测性。
7. **自研需建什么？** 财务模型/规则/例外、连接器、工单/证据、控制与运营；不只是一套 bot runtime。
8. **Build/Buy？** 自研垂直语义与体验；复用工作流、浏览器、OCR/LLM、IAM/Vault、可观测底座。
9. **ROI 怎么算？** 用可实现现金收益减 TCO；对直通率、人工例外时间和工时现金化做敏感性分析。
10. **最大难点？** 业务规则/例外治理、UI 与系统变更、内控/凭证、客户定制和价值现金化；不是 OCR demo。
11. **2–3 年走向？** AI + Workflow + API + RPA + Human 的分层自治；computer use 是补充，不是无约束替代。
12. **从何切入？** 单一 ICP 的对账与凭证控制塔，用 3 个设计伙伴、5 个限定场景和可量化退出标准验证。

### 24.2 财务 RPA 是否值得做？

**有条件地值得。** 若目标是通用横向 RPA、靠录制器和低价竞争，答案偏否；若能进入一个高交易量垂直行业、掌握财务例外和 ERP/银行连接器、把合规证据做成产品，答案偏是。传统 RPA 没过时，但已从“平台主角”退为混合执行层。

### 24.3 一页行动清单（开发者/小团队）

**未来 0–30 天**

- 选择一个 ICP：例如年处理 ≥10 万张发票或 ≥100 万条流水、拥有共享中心、1–2 个主 ERP 的制造/零售集团。
- 找 3 个设计伙伴，获取脱敏样本；记录 4 周基线：量、人工分钟、例外 reason、错误/重工、关账时间、系统变更。
- 只选一个闭环：建议银行/回款对账，或 AP 发票校验+三单匹配；签字确认成功条件与 SoD。
- 做 Build/Buy spike：Temporal、Playwright、一个 ERP 接口、一个 OCR；用 500–2,000 条黄金集比较端到端正确率和成本。

**未来 31–90 天**

- 先交付 canonical schema、规则、例外工单、证据包和 shadow 模式；再接写入。
- 建立 provider/connector contract、幂等、独立回读、Vault、审计和业务 SLI。
- AI 只做抽取、分类、候选和解释；低置信度/高风险全部人工复核。
- 每周输出价值表：直通率、人工分钟/单、错误率、每千单成本、MTTR；不能改善就缩场景而非堆功能。

**未来 3–6 个月**

- 达到第 19.4 节退出标准后，从一个实体扩到第二实体，验证模板复用率和 connector 维护成本。
- 形成 10–20 个标准 reason code、100+ 回归样本、部署/回滚手册和审计证据模板。
- 以“平台基础费 + 处理量 + 场景/连接器 + 实施”签首批合同；单独核算实施毛利。

**停止条件**

- 3 个设计伙伴都无法提供稳定 owner/样本/基线；目标流程例外率长期 >50% 且无 Pareto；每家都需改核心数据模型；客户只愿为一次性实施付费；或高风险动作无法获得内控批准。触发任一项，应缩窄行业/场景或停止平台化投入。

## 附录 A：API、脚本、RPA、Workflow、Agent、人工的决策树

```text
任务是否需要系统动作？
├─ 否 → 只是一次性数据变换且可复核？
│       ├─ 是 → 脚本
│       └─ 否 → 人工/分析工具
└─ 是 → 是否有受支持、权限可控的 API/批量接口？
        ├─ 是 → API 集成
        │       └─ 是否跨时长、需等待/审批/补偿/SLA？
        │               ├─ 是 → Workflow 编排 API（必要时 Human Task）
        │               └─ 否 → 服务/脚本 + 调度
        └─ 否 → UI 是否稳定、规则明确、成功可独立验证？
                ├─ 是 → RPA；外层仍用 Workflow/审计
                └─ 否 → 是否主要因为文档/语言/例外不确定？
                        ├─ 是 → Agent/Document AI 生成候选
                        │       ├─ 低风险、可逆、高置信 → 策略允许后执行
                        │       └─ 高风险/不可逆/低置信 → 人工审批/处理
                        └─ 否 → 改造流程或人工，不强行自动化
```

## 附录 B：研究方法、局限与关键资料

1. 优先使用 2024–2026 的官方监管文本、厂商产品文档、官方客户案例和原始研究/论文；新闻转述只在原始付费报告不可公开访问时用于方向性数据。
2. 厂商能力表没有统一 hands-on benchmark，不能替代 PoC；公开价格不含地区税费、附加容量、实施、支持和合同折扣。
3. 市场数字因定义差异不可直接合并；“财务 RPA 企业采用率”缺少可信统一统计，已明确标注。
4. 案例效果来自供应商/客户披露，未独立审计；缺少成本时不推算 ROI。
5. 中国电子凭证方向参考财政部 2025 年推广通知与[应用指南](https://kjs.mof.gov.cn/zt/kuaijixinxihuajianshe/dzpzkjsjbzshsd/czznhjswd/202505/t20250519_3964019.htm)；系统设计还应结合 2024 年[会计信息化工作规范](https://www.mof.gov.cn/jrttts/202408/t20240809_3941452.htm)。
6. Agent 安全框架可参考 [NIST AI RMF 与 GenAI Profile](https://www.nist.gov/itl/ai-risk-management-framework)；computer use 的厂商文档也明确要求对金融交易等高后果动作进行人工确认，[Anthropic Computer Use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)。

### 最终判断的置信度

| 判断 | 置信度 | 主要不确定性 |
|---|---|---|
| RPA 市场仍增长且不会在 2–3 年消失 | 高 | 市场定义和厂商收入分类变化 |
| AI 不会短期替代高风险财务 RPA/Workflow | 高 | computer-use 能力提升速度 |
| 垂直控制塔优于通用 RPA 新平台 | 中高 | 团队行业渠道、客户设计伙伴质量 |
| 6–8 人 5–7 个月可做限定 MVP | 中 | 目标 ERP、私有化/安全要求与样本质量 |
| 对账/发票校验是最佳普适切口 | 中高 | 特定行业的付款、税务或报表痛点可能更强 |
