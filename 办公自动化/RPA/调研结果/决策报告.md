# Deliverable 8｜CTO Go / No-Go 决策报告

## 1. 一页结论

### Go，但不是“通用 RPA 平台 Go”

**Go：** 做 Finance Native Automation，面向有财务共享中心、交易量大、系统多且有稳定流程 owner 的制造、零售、电商、物流和集团企业；先做银行对账 + AP 发票校验/三单匹配。

**No-Go：** 做全行业通用录制器、同时覆盖所有 ERP/银行、让 Agent 直接付款、首版自研 durable workflow/OCR/LLM/流程挖掘，或在没有真实设计伙伴和可现金化基线时先造平台。

## 2. Finance Native 是否是壁垒

“AI + RPA”不是壁垒，因为所有主要厂商都已在宣传 agentic automation、Document AI 或 Copilot。真正可持续的 Finance Native 壁垒是：

```text
财务对象模型（Invoice/BankTxn/Journal/PO）
        ↓
规则/容差/会计期间/SoD 策略
        ↓
连接器版本矩阵（ERP/银行/税务）
        ↓
例外 reason code + 处置语料
        ↓
证据包、反冲、审计重建和价值指标
        ↓
跨实体模板复用与持续运营数据
```

它的壁垒来自数据和交付闭环，而不是模型品牌或节点数量。**中高置信判断：** 通用 RPA 的控制面仍是必要底座，但财务场景的规则、证据和连接器深度决定购买与续费。

## 3. 生产级整体架构

```text
                    Web Console / Finance Workbench
                                  │ OIDC/MFA
                           API Gateway / BFF
          ┌───────────────────────┼────────────────────────┐
          ↓                       ↓                        ↓
   Workflow/Policy          Finance Domain             AI Gateway
   DSL/Version/Approval      Match/Invoice/Journal      RAG/OCR/Agent
          │                       │                        │
          └───────────────┬───────┴───────────────┬────────┘
                          ↓                       ↓
                 Temporal/Camunda                Tool Gateway
                 workflow/task queue        (allowlist + policy)
                          ↓                       ↓
                 Job Dispatcher / Lease / Scheduler
                    ┌──────────────┼──────────────┐
                    ↓              ↓              ↓
              Linux API Worker  Playwright      Windows .NET UIA
                    │              │              │
                    └───────┬──────┴──────┬───────┘
                            ↓             ↓
                  ERP / Bank / Tax / OA / Email / Excel

  PostgreSQL（控制/业务元数据）  Redis（缓存/限流）  Object Store（文件/证据）
  Vault/KMS（secret）  OpenTelemetry → Prometheus/Grafana/Loki/SIEM
```

### 3.1 每个组件为什么存在

| 组件 | 存在理由 | 不用它的后果 |
|---|---|---|
| API Gateway/BFF | 认证、租户、限流、统一错误与审计 | 各服务权限不一致、难治理 |
| Workflow Service | 版本、状态、等待、审批、补偿 | RPA 脚本无法恢复/审计 |
| Finance Domain | 统一财务对象、容差、匹配、反冲 | 每个客户重复写规则，错误不可比 |
| Tool Gateway | Agent 与执行权限的唯一闸门 | Prompt 注入可直达系统 |
| Temporal/Camunda | durable timer、event history、task queue | Worker 崩溃后无法安全续跑 |
| Scheduler/Queue | 事件、定时、优先级、并发和租约 | 峰值堵塞、重复处理 |
| Worker Supervisor | 机器心跳、签名包、升级、隔离 | Bot 停机/版本漂移不可见 |
| PostgreSQL | 事务元数据、RLS、查询与索引 | 依赖文件/Redis，无法一致审计 |
| Redis | 短期锁、缓存、限流、幂等热路径 | 只能用 DB 承担低延迟协调 |
| Object Store | 大文件、截图、原始凭证、录像 | 数据库膨胀、成本高、难留存 |
| Vault/KMS | secret 保管、轮换、JIT lease | 密码进入流程/日志，审计失效 |
| OTel/Prometheus/Grafana | trace、指标、告警、跨节点定位 | 只能看到“失败”，找不到业务原因 |
| SIEM/WORM | 安全事件和不可变审计 | 关键证据可被删除/改写 |

## 4. SaaS 与私有化部署

### 4.1 SaaS

```text
User Browser
  → Edge/WAF → API Gateway
  → Regional Control Plane（tenant isolation）
     ├─ PostgreSQL（分片/逻辑租户 + RLS）
     ├─ Temporal cluster / worker pool
     ├─ AI gateway（区域/供应商路由）
     └─ Object Store / Vault / SIEM
  → Customer Connector Agent（企业内网 outbound only）
     ├─ API/SFTP worker
     └─ Windows UIA/Playwright worker
  → ERP / Bank / Tax / OA
```

关键要求：区域内数据处理、客户网络不开放入站、connector agent 证书轮换、租户级密钥和对象存储前缀隔离、按租户限流/预算、控制面与执行面故障隔离。

### 4.2 私有化

```text
企业内网/受控 K8s
├─ Ingress/API Gateway
├─ Control Plane + Temporal/Camunda
├─ PostgreSQL HA + Redis Sentinel/Cluster
├─ S3/MinIO Object Store + WORM/备份
├─ Vault/KMS/HSM + 企业 LDAP/OIDC
├─ Linux API/AI Workers
├─ Windows VM Pool + signed agent
└─ OTel Collector → 企业 Prometheus/Grafana/SIEM
```

AI 选择本地模型、企业 VPC endpoint 或禁用；升级采用离线签名包、preflight migration、canary namespace、可回滚 schema/app/worker。高可用只在控制面/数据库/对象存储达到设计标准后宣称；Windows 运行池需按账户/应用会话做容量和灾备演练。

## 5. 安全设计

### 5.1 Bot 的 ERP 密码放在哪里

放在企业 Vault/KMS/HSM 或受支持的云 Secret Manager 中。数据库仅保存 `secret_ref`、owner、scope、rotation_due、last_used_at；Workflow 只引用 connection id；Worker 通过 mTLS/workload identity 申请短期 lease，在内存中使用，禁止打印、截图、持久化和返回 API。密码轮换由 Vault/企业 PAM 触发，失效后让相关任务进入 `SECRET_UNAVAILABLE`，不能把新密码写回 DSL。

### 5.2 防止恶意改流程后自动付款

1. Draft/Review/Published/Retired 状态机；生产版本不可变。
2. 修改需要 `workflow:write` + 业务 owner review；高风险流程需安全/内控双签。
3. 发布物包含 DSL、编译计划、Activity/connector/model 版本 hash，使用组织签名；Worker 验签并拒绝未签包。
4. Policy-as-code 另存且版本化；任何付款节点没有 approval、SoD、限额、账户白名单或 idempotency key 时编译失败。
5. 生产变更先 shadow/canary；write 权限 token 在审批后短时签发；每日金额/笔数预算熔断。
6. 审计日志和事件写入 append-only/WORM/SIEM；管理员也不能删除运行证据。

## 6. 可靠性与可观测性

### 6.1 Exactly-once 的现实

跨 ERP、银行、邮件的 exactly-once 通常不可获得。实现“effectively-once”：业务幂等键 + outbox/inbox + 外部回读 + lease + 去重 webhook + 补偿/反冲。数据库事务只保证本地状态，不保证外部系统同时提交。

### 6.2 每层记录什么

| 层 | 记录 | 不直接记录 |
|---|---|---|
| Workflow | execution_id、workflow/version、tenant/entity、状态、policy/rule 版本、耗时 | 原始发票全文、密码、完整 prompt |
| Node | node_id、attempt、status、输入/输出 hash、重试/错误码 | 完整银行卡号、个人证件号 |
| Activity | connector/activity version、request/response hash、外部业务号、receipt | Authorization header、secret、完整网页 DOM |
| RPA | machine/OS/runtime、窗口/selector 摘要、截图引用、下载 hash | 含凭证字段的未脱敏截图/录像 |
| AI | model/provider/version、prompt hash、retrieval ids、tool call、confidence、cost | 未授权原文和隐藏系统提示 |
| Human | reviewer、assurance/MFA、decision、comment hash、时间、SoD 结果 | 超出业务必要性的个人信息 |

全链路使用 `trace_id + execution_id + node_id + attempt`；敏感证据在对象存储单独加密，日志只保存引用和脱敏摘要。

### 6.3 SLO

- 控制面 API 可用性 ≥99.9%（试点可 99.5%）。
- 关键执行端到端正确率 ≥99.5%，不是仅“bot status=success”。
- 运行证据完整率 100%；审计检索 P95 ≤5 秒，单案重建 ≤5 分钟。
- Worker heartbeat/lease 延迟、队列等待 P95、外部响应 P95、重试率、unknown side effect 数、MTTR、每千单成本均进入仪表盘。

## 7. 开源 vs 自研

| 模块 | 推荐 | 开源/商业 | 自研？ | 原因 |
|---|---|---|---|---|
| Workflow | Temporal；BPMN 需求强时 Flowable/Camunda | Temporal MIT；Flowable Apache 2；Camunda 商业边界需核验 | 只做封装/财务节点 | durable execution 不应重造；[Temporal](https://docs.temporal.io/)、[Flowable](https://www.flowable.com/open-source-code) |
| Browser | Playwright | Apache 2 | 封装 Activity/selector 策略 | 浏览器协议和兼容性复用；[Playwright](https://playwright.dev/docs/locators) |
| Excel | openpyxl/pandas/OpenXML + Windows COM bridge | 开源 + Microsoft | 自研财务校验/进程监督 | 格式/公式边界复杂，业务校验是核心 |
| OCR | PaddleOCR + 云 OCR adapter | Apache 2/商业 API | 不训练基础模型；自研路由/eval | 模型易商品化；[PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR) |
| MQ | Temporal queue；必要时 RabbitMQ/Kafka | 开源/托管 | 不自研 broker | 先控制组件数，按规模演进 |
| DB | PostgreSQL | PostgreSQL License | 自研 schema/RLS/审计 | 财务对象/约束是产品核心 |
| Scheduler | Temporal schedule/事件 | 开源/托管 | 场景触发适配 | 可靠 timer 已有实现 |
| Secret | Vault/KMS/HSM/企业 PAM | 开源/商业 | No | 认证、轮换、硬件密钥不应自造 |
| Observability | OTel + Prometheus/Grafana/Loki | Apache 2/开源 | 自研业务指标/脱敏 exporter | 统一标准与企业栈集成 |
| LLM | 多供应商 gateway + 私有模型选项 | 商业 API/开源模型 | 自研 policy/eval/router | provider-neutral，控制数据和成本 |

## 8. 竞争对手与差异化

### UiPath 强在哪里

Runtime/Studio/Orchestrator/Document/Mining/治理全栈，成熟生态和复杂企业部署；公开文档显示其 Job、Robot、Machine、Credential、Queue 语义已细化。不要正面复制其平台面积。

### Power Automate 强在哪里

Microsoft 365、Dataverse、Azure、Dynamics、Entra、Windows 365 的分发和连接器优势；Hosted Machine Group 可按队列和容量扩缩。不要与其争通用低代码入口。

### 国内 RPA 强在哪里

中文、本地私有化、国产化、税务/银行/本地 ERP 适配、交付关系和政企采购；技术公开基准较少，应以真实 PoC 比较。

### 共同弱点与我们的机会

共同弱点（**推断，不是统一客户调查**）：通用平台需要大量实施；财务规则、例外、内控证据和 ROI 归因常由客户/伙伴二次建设；跨客户的财务语义复用不足。

我们的具体差异化：

```text
Finance-native objects
  → reconciliation/matching engine
  → policy-as-code + SoD + amount/entity controls
  → evidence pack + reversals + audit reconstruction
  → bank/ERP/local tax connector certification
  → exception corpus + measurable touchless/MTTR/TCO
```

## 10. 最终 CTO 问答

| 问题 | 结论 |
|---|---|
| 应该做什么？ | Finance Native 对账/发票控制塔，而非通用 RPA |
| 不应该做什么？ | 全量平台、任意脚本、Agent 直付、首版自研基础设施 |
| 第一批客户？ | 有共享中心、交易量大、1–2 个主 ERP、愿提供脱敏数据和 owner 的制造/零售/电商集团 |
| 第一批场景？ | 银行对账 + 发票校验/三单匹配；报表 Excel 作为辅助入口 |
| MVP？ | 受限 DSL、Temporal、Playwright、Excel/HTTP、队列、RBAC/Vault、例外工单、证据包 |
| 技术栈？ | React/TS、Go（或 Java）、Temporal、C# UIA、Playwright、Python 文档、PostgreSQL、Redis、S3、Vault、OTel |
| 人力/时间？ | 5 人约 3 个月只做可运行 MVP；产品化试点 6–8 人 5–7 个月 |
| 最大技术风险？ | 静默财务错误、unknown side effect、UI/ERP 变更和敏感数据/Agent 越权 |
| 最大商业风险？ | 每个客户变定制项目，工时节省不能现金化，通用厂商降价下沉 |
| 最大竞争对手？ | UiPath（全栈）、Power Automate（分发/生态）、国内交付型 RPA（本地化） |
| 最大差异化？ | 财务对象/规则/例外/证据/连接器的闭环，而不是 AI 标签 |
| 三年演进？ | 控制塔→多域财务→分层自治；始终 API/Workflow/RPA/Agent/Human 混合 |

## 11. Go/No-Go 门槛

**Go 条件：** 至少 2 个设计伙伴；每个有 ≥10 万笔/年或明显关账/对账痛点；能提供脱敏样本、业务 owner、内控审批；PoC 可达到 ≥70% 直通、≥99.5% 端到端正确完成率、证据 100% 完整；客户能把节省转成加班/外包/避免招聘/扩容中的至少一项现金价值。

**No-Go 条件：** 没有稳定流程 owner；样本无法合规获得；所有流程例外率 >50%；必须先覆盖任意 ERP/银行；客户只愿为一次性脚本付费；付款/记账控制无法获得 SoD 批准；或团队没有 Windows/财务域运营能力。

### 最终决策

> **有设计伙伴和可现金化基线：Go，立即做“银行对账 + AP 发票控制塔”。**
>
> **没有上述条件：No-Go，先做 2–4 周 discovery/影子 PoC，而不是开始搭建通用平台。**
