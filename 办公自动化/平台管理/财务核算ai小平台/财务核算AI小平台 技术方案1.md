## 一、项目概述

### 1.1 平台定位

财务核算AI小平台定位为财务核算的AI辅助工具层，处于业务前端系统与YS财务系统之间，承担以下核心职能：

- 业务数据处理：自动采集、清洗、结构化业务前端数据（如工资表、发票、收付款流水等）
- AI凭证生成：基于业务数据，按会计准则与集团科目体系，自动生成标准会计凭证
- 凭证推送审核：将生成的凭证推送至YS系统，进入YS既有的审核流程
- 多主体支持：按主体维度隔离与处理

### 1.2 三层架构概述

平台采用三层架构，自上而下分别为：

| 层级 | 组件 | 职责说明 |
|------|------|----------|
| Agent层 | 工资处理Agent、发票匹配Agent、账务处理Agent、审核推送Agent、数据校验Agent、异常监控Agent | 各Agent负责特定业务场景的自动化处理，接收输入数据、执行业务规则、产出结构化结果 |
| 核心服务层 | 凭证引擎、主体路由、科目映射、规则引擎、数据中枢 | 凭证引擎负责生成标准凭证；主体路由按主体分发；科目映射维护业务场景到会计科目的映射规则；数据中枢管理缓存与状态 |
| 对接层 | YS API适配器、认证管理、重试/回调、日志审计 | 封装YS系统API调用，处理认证、请求重试、状态回调，对外屏蔽YS接口细节 |

## 三、Agent层详细设计

### 3.1 Agent框架选型

基于财务场景的稳定性和数据安全要求，技术选型如下：

| 组件 | 技术选型 | 说明 |
|------|----------|------|
| Agent框架 | LangChain 1.0 | 核心Agent逻辑构建、工具封装 |
| Agent运行时 | LangGraph | Agent协同流程编排、状态持久化、人机协同 |
| 大模型 | 私有化部署（Qwen2.5等） | 财务数据不出域，满足安全合规要求 |
| 任务调度 | Celery + Redis | 异步任务队列，支持Agent串行/并行执行 |

**选型依据**：
- LangGraph是底层运行时，提供持久化执行、流式传输、人机协同、状态可恢复等生产级能力，适合工资核算等需要审批门禁的长流程场景
- LangChain提供标准抽象（模型、工具、Agent循环），适合快速开发工资处理、数据校验等具体Agent
- 一期从LangGraph + LangChain组合起步

### 3.2 Agent职责与实现要点

| Agent | 输入 | 处理逻辑 | 输出 | 研发工作量 |
|-------|------|----------|------|------------|
| 工资处理Agent | Excel工资表 | 解析→主体识别→按成本中心拆分→生成待校验凭证 | 结构化凭证数据 | 2人周 |
| 发票匹配Agent | 发票清单+流水 | OCR/结构化→三单匹配→生成凭证 | 匹配结果+凭证 | 3人周 |
| 账务处理Agent | 业务单据 | 按场景调规则引擎→生成分录 | 完整凭证 | 2人周 |
| 数据校验Agent | 凭证数据 | 借贷平衡+科目有效性+辅助核算校验 | 校验报告 | 1人周 |
| 审核推送Agent | 校验通过凭证 | 调用YS API→记录凭证号→轮询状态 | 推送结果+状态 | 2人周 |
| 异常监控Agent | 全流程日志 | 异常检测→告警→触发人工介入 | 告警通知 | 1人周 |

### 3.3 Agent协同流程（以工资为例）

基于LangGraph状态图，设计为6个节点 + 1个审批门禁：

| 步骤 | Agent/节点 | 动作 |
|------|-----------|------|
| 1 | loader（确定性代码） | 接收工资表 → 解析 → 按主体拆分 → 校验基础格式 |
| 2 | 工资处理Agent | 调用薪酬计算工具逐员工计算工资，处理边缘情况 |
| 3 | 数据校验Agent | 重新计算与Agent结果Diff校验 + 异常标记 |
| 4 | aggregator（确定性代码） | 汇总生成待审批摘要（总金额、人数、异常项） |
| 5 | approval_gate（审批门禁） | LangGraph interrupt()暂停执行，等待人工审批 |
| 6 | executor（确定性代码） | 审批通过后生成标准凭证 → 调用YS API推送 |
| 7 | 异常监控Agent | 若推送失败/审核驳回 → 告警 → 财务处理 |

流程图：

```
[工资表上传] → loader → 工资处理Agent → 数据校验Agent → aggregator → 
                     ┌─────────────────┐
                     │  approval_gate  │ (interrupt等待人工审批)
                     └────────┬────────┘
                              │
              approve ────────┴──────── reject
                 ↓                         ↓
              executor                   rejected
         (推送YS/写凭证)            (标记驳回+审计)
```

### 3.4 核心代码结构示例

```python
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.postgres import PostgresSaver
from langchain.agents import create_agent
from langchain.tools import tool

# ---------- 状态定义 ----------
class PayrollState(TypedDict):
    file_id: str
    tenant_id: str
    raw_data: list[dict]          # 解析后的工资原始数据
    employee_calculations: list[dict]  # 每个员工的计算结果
    validation_report: dict       # 校验报告
    summary: str                  # 审批摘要
    approval_status: str          # pending / approved / rejected
    voucher: dict                 # 最终生成的凭证
    ys_task_id: str               # YS推送任务ID

# ---------- 1. Loader（确定性代码） ----------
def loader_node(state: PayrollState):
    raw = parse_payroll_excel(state["file_id"])
    return {"raw_data": raw}

# ---------- 2. Calc Agent（LangChain Agent） ----------
@tool
def payroll_calc(employee_id: str, base_salary: float, attendance_days: int, 
                 sick_days: int, overtime_hours: float, tax_bracket: str) -> dict:
    """确定性工资计算工具，模型只做参数组装，计算由代码完成"""
    return {"gross": ..., "net": ..., "deductions": [...]}

calc_agent = create_agent(
    model="qwen2.5:7b",
    tools=[payroll_calc],
    system_prompt="你是工资核算助手。根据员工信息和考勤数据，调用payroll_calc工具计算工资。"
)

def calc_agent_node(state: PayrollState):
    results = []
    for emp in state["raw_data"]:
        result = calc_agent.invoke({"employee": emp})
        results.append(result)
    return {"employee_calculations": results}

# ---------- 3. Validator（确定性Diff + LLM异常标记） ----------
def validator_node(state: PayrollState):
    diffs = recompute_and_diff(state["employee_calculations"])
    anomalies = llm_mark_anomalies(diffs)
    return {"validation_report": {"diffs": diffs, "anomalies": anomalies}}

# ---------- 4. Aggregator（汇总摘要） ----------
def aggregator_node(state: PayrollState):
    summary = generate_summary(state["employee_calculations"], state["validation_report"])
    return {"summary": summary}

# ---------- 5. Approval Gate（LangGraph interrupt） ----------
def approval_gate_node(state: PayrollState):
    response = interrupt({
        "summary": state["summary"],
        "total_amount": sum(emp["net"] for emp in state["employee_calculations"]),
        "employee_count": len(state["employee_calculations"]),
        "anomalies": state["validation_report"]["anomalies"]
    })
    return {"approval_status": response["decision"]}

# ---------- 6. Executor（凭证生成 + YS推送） ----------
def executor_node(state: PayrollState):
    voucher = generate_voucher(state["employee_calculations"])
    ys_result = push_to_ys(voucher, state["tenant_id"])
    return {"voucher": voucher, "ys_task_id": ys_result["task_id"]}

# ---------- 构建LangGraph ----------
builder = StateGraph(PayrollState)
builder.add_node("loader", loader_node)
builder.add_node("calc_agent", calc_agent_node)
builder.add_node("validator", validator_node)
builder.add_node("aggregator", aggregator_node)
builder.add_node("approval_gate", approval_gate_node)
builder.add_node("executor", executor_node)
builder.add_node("rejected", lambda s: {"approval_status": "rejected"})

builder.set_entry_point("loader")
builder.add_edge("loader", "calc_agent")
builder.add_edge("calc_agent", "validator")
builder.add_edge("validator", "aggregator")
builder.add_edge("aggregator", "approval_gate")

builder.add_conditional_edges(
    "approval_gate",
    lambda s: "executor" if s["approval_status"] == "approved" else "rejected"
)
builder.add_edge("executor", END)
builder.add_edge("rejected", END)

# ---------- 持久化Checkpointer ----------
checkpointer = PostgresSaver.from_conn_string("postgresql://...")
graph = builder.compile(checkpointer=checkpointer)
```

### 3.5 关键设计要点

1. **确定性计算与LLM分离**：实际金额计算用确定性代码，LLM负责参数组装和边缘情况推理，杜绝"模型胡编数字"风险
2. **审批门禁持久化**：使用PostgresSaver作为LangGraph检查点，审批暂停状态持久化到数据库，服务重启后可恢复
3. **校验双重保障**：确定性Diff校验（硬规则）+ LLM异常标记（软规则），既保准确性又保灵活性
4. **私有化模型部署**：使用Ollama部署Qwen2.5等开源模型，财务数据不出内网
5. **可观测性**：集成LangSmith或自建日志系统，记录每一步Agent的输入输出

## 四、核心服务层详细设计

### 4.1 凭证引擎设计

凭证引擎是核心业务逻辑层，负责将业务数据转换为符合会计准则的标准凭证：

```
┌─────────────────────────────────────────────────────┐
│                    凭证引擎                          │
│  ┌───────────────────────────────────────────────┐ │
│  │  1. 数据标准化  →  字段映射、格式统一         │ │
│  │  2. 科目匹配    →  基于科目映射表智能匹配     │ │
│  │  3. 凭证生成    →  借/贷分录生成             │ │
│  │  4. 完整性校验  →  必填项、借贷平衡          │ │
│  │  5. 凭证编号    →  按主体+日期生成唯一编号   │ │
│  └───────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘
```

### 4.2 科目映射表设计

| 字段 | 类型 | 说明 |
|------|------|------|
| scene_code | VARCHAR(32) | 业务场景编码（如WAGE_2026） |
| source_field | VARCHAR(64) | 源数据字段名 |
| source_value_pattern | VARCHAR(128) | 匹配模式（正则/通配） |
| target_account_code | VARCHAR(20) | 目标科目编码 |
| target_account_name | VARCHAR(100) | 目标科目名称 |
| is_debit | BOOLEAN | 借/贷方向 |
| priority | INT | 匹配优先级 |
| tenant_id | VARCHAR(32) | 主体维度隔离 |

## 五、YS API对接层设计

### 5.1 对接策略

```
┌─────────────────────────────────────────────────────────────┐
│                    YS API适配器                              │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │  认证管理  →  Token获取/刷新（OAuth2/API Key）        │ │
│  │  凭证推送  →  POST /api/voucher/create                │ │
│  │  状态查询  →  GET /api/voucher/status/{id}            │ │
│  │  回调处理  →  接收YS审核结果回调                      │ │
│  │  重试机制  →  指数退避重试（3次，间隔1s/5s/30s）     │ │
│  │  熔断降级  →  连续失败5次，暂停推送，人工介入        │ │
│  └─────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 关键接口设计

| 接口 | 方法 | 说明 |
|------|------|------|
| pushVoucher(voucher, tenant) | POST | 推送凭证至YS对应账套 |
| queryVoucherStatus(ysVoucherId) | GET | 查询凭证审核状态 |
| handleCallback(payload) | POST | 接收YS异步审核结果回调 |
| syncAccountMapping() | GET | 同步YS科目体系（初始化/定期） |

### 5.3 档案映射方案

**建议方案：独立维护映射表 + 定时同步**

1. 科目映射：平台内维护"业务场景→YS科目编码"映射表，由财务负责人配置
2. 辅助核算映射：如部门、项目、客户等，通过映射表关联YS档案ID
3. 定时同步：每日定时从YS拉取最新科目/档案变更，更新映射缓存
4. 映射冲突处理：提供管理界面，人工确认冲突项

### 5.4 技术决策讨论

| 讨论项 | 技术建议 | 依据 |
|--------|----------|------|
| 分贝通/合思集成 | 优先通过API对接，不依赖其Agent能力 | 数据安全性要求，财务数据应保留在平台内闭环处理 |
| 金融保理凭证 | 先做表格导入→规则生成；后期对接金融系统API | 分阶段交付，降低复杂度 |
| 发票与收入映射 | 发票匹配Agent + 科目映射规则 | 需业务方提供映射规则，技术侧提供规则配置界面 |
| 税金表格生成 | 可复用账务处理Agent，需单独维护税金科目映射 | 规则由财务提供 |
| 财报波动AI分析 | 独立分析Agent，调用大模型做趋势解读 | 需求较新，建议二期实现 |

## 六、交互设计方案

### 6.1 交互设计原则

| 原则 | 说明 |
|------|------|
| 人机协同 | Agent处理重复性工作，关键决策点交由人工确认 |
| 可视可审计 | 每一步操作都有迹可循，审批过程完整记录 |
| 渐进式介入 | 低风险操作静默执行，高风险操作必须人工确认 |
| 责任清晰 | Agent出建议，人做决定，责任边界明确 |

### 6.2 前端技术选型

采用FastAPI后端 + React前端组合，通过AG-UI协议驱动LangGraph工作流：

| 组件 | 技术选型 | 说明 |
|------|----------|------|
| 前端框架 | React + TypeScript | 配合Ant Design UI库 |
| Agent通信协议 | AG-UI（SSE流式） | 实时接收中断事件和工作流进度 |
| 中断组件渲染 | langgraph-ui-components | 内置ask_user中断组件渲染能力 |
| 审批卡片 | 自定义组件注册 | 工资审批、凭证审核等场景卡片 |

### 6.3 核心功能页面设计

#### 6.3.1 工作台与任务中心

财务人员登录后的首页，核心是让待办事项一目了然：

| 模块 | 设计要点 |
|------|----------|
| 关键指标卡 | 显示"待审批凭证数"、"待处理异常"、"本月已推送YS凭证"等汇总数据 |
| 待办任务列表 | 按优先级列出所有需要人工介入的任务，点击进入审批详情页 |
| 系统状态 | 展示Agent运行状态、YS系统连接状态 |

#### 6.3.2 上传与任务发起页

以"工资表上传"为例：

- 文件上传区：支持拖拽或点击上传Excel/CSV文件
- 主体与场景选择：明确选择凭证所属的主体和业务场景
- 提交与进度：提交后展示Agent处理进度条，处理到"待审批"状态时主动提示

#### 6.3.3 凭证审批详情页

这是最核心、使用频率最高的页面：

| 区域 | 内容 |
|------|------|
| 顶部信息摘要 | 凭证号、主体、制单人、提交时间、总金额 |
| 凭证分录表格 | 借贷格式展示科目、摘要、金额，异常数据高亮标记 |
| Agent处理信息 | 数据来源、映射依据、AI解释（可点击查看） |
| 底部操作区 | 审批通过（二次确认）、驳回（填写理由）、查看源数据 |

## 七、Agent方案与传统开发对比分析

### 7.1 Agent的核心作用

在当前设计中，Agent的核心作用是**结构化数据处理与凭证生成的智能化执行层**，具体如下：

| Agent | 核心作用 | 实质能力 |
|-------|----------|----------|
| 工资处理Agent | 解析Excel工资表，按主体拆分，生成凭证 | 识别表头、理解字段语义、处理格式差异 |
| 发票匹配Agent | 发票与流水/订单的三单匹配 | 处理模糊匹配、识别异常匹配项 |
| 账务处理Agent | 将业务单据转为会计分录 | 根据业务场景语义判断科目归属 |
| 数据校验Agent | 校验凭证完整性与合规性 | 识别规则覆盖不到的边缘异常 |
| 审核推送Agent | 对接YS API，推送并追踪状态 | 智能重试策略判断 |
| 异常监控Agent | 全局异常捕获与告警 | 多源日志语义理解，判断告警优先级 |

### 7.2 核心差异对比表

| 维度 | Agent方案（LangGraph + LLM） | 传统开发方案（纯代码 + 规则引擎） |
|------|------------------------------|--------------------------------|
| 输入适应性 | 可处理字段名变体，通过语义理解自动匹配 | 需硬编码字段映射，模板变更需开发介入 |
| 异常处理 | 可识别"合理但异常"的情况，给出提示 | 只能处理预设异常，超出规则直接报错 |
| 凭证生成逻辑 | 理解业务描述文本，判断科目归属 | 所有逻辑编码为if-else或规则表 |
| 维护成本 | 规则变更多通过Prompt调优，迭代速度快 | 代码变更+测试+部署，迭代周期长 |
| 决策解释性 | 可输出自然语言解释 | 需额外编写解释逻辑 |
| 开发人力 | 一期约4-6人 | 同样功能范围约3-4人（但后续维护成本高） |
| 冷启动速度 | 有基础模型，少量标注数据即可工作 | 需完整梳理所有业务规则后才能开发 |

### 7.3 详细场景对比：工资表解析

**场景**：HR上传的Excel工资表，本月多了一列"项目奖金"。

| | Agent方案 | 传统方案 |
|--|-----------|----------|
| 处理方式 | 理解"项目奖金"语义→自动映射到"应付职工薪酬-奖金" | 找不到"项目奖金"映射→报错"未知字段"，流程中断 |
| 应对耗时 | 无需代码变更，Agent自适应 | 需开发修改映射→测试→重新部署（0.5-1天） |
| 财务人员体验 | 提交→正常生成凭证 | 提交→报错→联系IT→等待修复→重新提交 |

### 7.4 详细场景对比：异常识别

**场景**：某部门本月平均工资环比上涨25%。

| | Agent方案 | 传统方案 |
|--|-----------|----------|
| 处理方式 | 识别偏离度→标记"⚠️异常项"→审批卡片高亮提示 | 按阈值（如>20%）触发硬报错→流程终止 |
| 处理结果 | 财务核实确认无误→通过；确认错误→驳回修改 | 需先让IT解除报错→再重新发起流程 |

### 7.5 Agent方案的核心优势

**对财务人员的价值：**

- 减少重复劳动：Agent完成90%的数据处理工作
- 降低出错概率：系统化规避人为录入的笔误/遗漏
- 缩短处理周期：从半天缩短到分钟级
- 提升决策质量：提供异常项提醒和生成依据

**对IT/研发的价值：**

- 减少定制开发：新场景只需调整Prompt/示例
- 降低维护负担：规则变更通过Prompt更新即可
- 快速响应业务：财务团队可自主调整部分规则
- 统一Agent框架：所有业务场景复用同一套框架

### 7.6 何时Agent方案不如传统方案

| 场景 | 原因 | 建议 |
|------|------|------|
| 输入高度标准化 | 数据格式完全固定，无变化 | 传统代码+简单规则即可 |
| 规则完全明确且少量 | 业务规则不超过10条 | 硬编码更快、更可控 |
| 实时性要求极高（<100ms） | LLM推理有延迟（1-5秒） | 使用传统代码或专用小模型 |
| 预算极其有限 | GPU服务器+模型部署有额外成本 | 先做传统方案 |
| 需要100%确定性输出 | 金融监管场景 | 纯规则引擎 |

### 7.7 结论：混合架构

本方案采用Agent + 确定性代码的混合架构：

```
┌─────────────────────────────────────────────────────────┐
│  确定性代码（保证准确性）                              │
│  ├── 金额计算（工资/税金）                            │
│  ├── 借贷平衡校验                                     │
│  ├── YS API调用                                       │
│  └── 科目编码匹配（可配置映射表）                     │
├─────────────────────────────────────────────────────────┤
│  Agent（处理灵活性和语义理解）                         │
│  ├── Excel语义解析（列名识别）                        │
│  ├── 异常模式识别（上下文判断）                       │
│  ├── 科目归属建议（业务描述理解）                     │
│  └── 审批摘要生成（自然语言）                         │
└─────────────────────────────────────────────────────────┘
```

Agent方案的核心优势是**用语义理解能力替代传统开发中大量繁琐、易碎、难以维护的硬编码规则**，让系统更柔性地适应业务变化，同时把确定性计算牢牢锁在代码层保证准确。

## 八、数据安全方案

### 8.1 加密体系

| 层级 | 措施 | 说明 |
|------|------|------|
| 传输层 | TLS 1.3 + 双向证书 | 所有API通信加密，防止中间人攻击 |
| 存储层 | AES-256 / 国密SM4 | 数据库敏感字段加密（金额、身份证号等） |
| 密钥管理 | KMS / HSM | 密钥集中管理，定期轮换 |

### 8.2 权限与审计

**权限模型：RBAC + 主体维度隔离**

| 角色 | 权限 |
|------|------|
| 系统管理员 | 全局配置，无数据访问 |
| 财务审核岗 | 查看凭证，不可修改 |
| 财务核算岗 | 查看+编辑本主体凭证 |
| 业务上传岗 | 上传数据，不可查看他人数据 |
| 审计岗 | 只读，所有操作留痕 |

**审计日志：**

- 谁 → 何时 → 对哪个凭证 → 做了什么操作
- 日志不可篡改（数据库WAL）
- 日志保留≥6年（会计法要求）

### 8.3 数据隔离

- 物理隔离：不同主体的数据存储在不同Schema/表，查询自动带tenant_id过滤
- 逻辑隔离：Agent调用时传递主体上下文，防止越权访问

### 8.4 大模型数据安全

- 私有化部署：使用Ollama等本地部署方案，财务数据不离开内网
- 敏感脱敏：输入大模型前，对姓名、身份证号等PII信息进行脱敏处理
- 输出审核：Agent输出结果需经过规则校验，防止"幻觉"导致错误分录

## 十、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| YS API不稳定/变更 | 推送失败 | 重试+熔断+降级，保留手动导出通道 |
| 大模型"幻觉"生成错误凭证 | 财务数据错误 | 凭证生成后必须经数据校验Agent校验；大模型输出仅作建议，不自动执行 |
| 财务规则变更频繁 | 科目映射失效 | 映射配置化+管理界面，财务自主维护 |
| 数据安全合规风险 | 法律风险 | 私有化部署+全链路加密+完整审计日志 |
| 工资计算规则变更 | 计算结果错误 | 将税率、社保比例等配置化，财务人员可自主维护 |
| LLM在Agent中不调用工具 | 结果不可控 | 强制要求逐员工调用工具；增加工具调用次数监控告警 |
| 审批中断后服务重启恢复失败 | 流程中断 | 使用Postgres Checkpointer，定期对中间状态做快照备份 |
